## Часть 1. Уязвимое веб-приложение

Технологии: **Python 3 + Flask + SQLite**, без внешних зависимостей, кроме Flask.

Функциональность: регистрация, вход, список комментариев, просмотр профиля пользователя.

### Реализованные уязвимости (OWASP Top 10:2021)

| № | Уязвимость | Категория OWASP | Где | Суть |
|---|------------|------------------|-----|------|
| 1 | **SQL Injection** | A03:2021 – Injection | `POST /login` | Логин/пароль подставляются в SQL-запрос через `%`-форматирование строк вместо параметризованного запроса. |
| 2 | **Stored XSS** | A03:2021 – Injection | `GET/POST /comments` | Текст комментария сохраняется и выводится в HTML без экранирования (`html.escape`/автоэкранирование не используются). |
| 3 | **IDOR / Broken Access Control** (дополнительно) | A01:2021 – Broken Access Control | `GET /profile/<id>` | Любой авторизованный пользователь может запросить профиль (включая пароль) произвольного `user_id`, без проверки, что это его собственный профиль. |

Соответствующие фрагменты кода отмечены в `app/app.py` комментариями
`# !!! УЯЗВИМЫЙ КОД ... !!!`.

### Запуск

```bash
cd app
python3 -m venv venv && source venv/bin/activate   # по желанию
pip install -r requirements.txt
python3 app.py
```

Приложение поднимется на `http://127.0.0.1:5000`.
При первом запуске автоматически создаётся файл `lab2.db` (SQLite)
и тестовые пользователи:

| username | password            | роль  |
|----------|---------------------|-------|
| admin    | SuperSecretAdminPass!23 | администратор |
| alice    | alicepass123        | обычный пользователь |
| bob      | bobpass456           | обычный пользователь |

## Часть 2. Эксплуатация уязвимостей

Скрипты находятся в `exploits/`, используют библиотеку `requests`
(`pip install requests`). Перед запуском убедитесь, что приложение
из части 1 запущено на `http://127.0.0.1:5000`.

### 2.1. SQL Injection — `exploit_sqli.py`

```bash
python3 exploits/exploit_sqli.py
```

Отправляет в поле `username` значение `admin' -- `, благодаря чему
условие проверки пароля в SQL-запросе «комментируется» и скрипт
входит в систему под учётной записью `admin`, не зная её настоящего
пароля.

### 2.2. Stored XSS — `exploit_xss.py`

```bash
python3 exploits/exploit_xss.py
```

Регистрирует тестового пользователя, публикует комментарий с
`<script>...</script>` и затем запрашивает страницу `/comments` от
имени «нового посетителя», показывая, что сервер вернул тег
`<script>` без экранирования — значит, в настоящем браузере он
выполнился бы у каждого, кто откроет страницу (кража cookies,
дефейс и т.д.).

### 2.3. IDOR — `exploit_idor.py` (дополнительная уязвимость)

```bash
python3 exploits/exploit_idor.py
```

Регистрирует обычного пользователя и, используя только его сессию,
перебирает `/profile/1`, `/profile/2`, `/profile/3`, читая email и
пароли чужих аккаунтов, включая администратора.

Все три скрипта протестированы и подтверждают эксплуатацию уязвимостей
в приложении из части 1 (вывод скриптов — см. ниже «Результаты
проверки»).

## Часть 3. Патч уязвимостей

Файл `patches/fix_vulnerabilities.diff` — unified diff, переводящий
`app/app.py` в безопасное состояние (эквивалент файла
`patches/app_patched.py`, оставленного для справки).

### Применение патча

```bash
cd lab2
patch -p1 < patches/fix_vulnerabilities.diff
# либо, если репозиторий — git-репозиторий:
git apply patches/fix_vulnerabilities.diff
```

### Что исправлено

1. **SQL Injection** — запрос в `/login` переписан на
   параметризованный (`cur.execute(query, (username, password))`),
   значения никогда не подставляются в текст SQL напрямую.
2. **Stored XSS** — вывод имени пользователя и текста комментария
   экранируется функцией `html.escape()` перед вставкой в HTML.
3. **IDOR** — в `/profile/<user_id>` добавлена проверка:
   доступ разрешён, только если `user_id` совпадает с
   `session['user_id']`, либо если пользователь — администратор
   (`session['is_admin']`); иначе возвращается `403 Forbidden`.
   Из профиля также убран вывод пароля в открытом виде.

### Проверка патча

После применения патча и перезапуска приложения повторный запуск
скриптов из `exploits/` должен показывать, что атаки больше не
проходят:

- `exploit_sqli.py` → `Успешный вход без знания пароля: False`
- `exploit_xss.py` → `Payload не найден в ответе без изменений`
- `exploit_idor.py` → все запросы `/profile/<id>` чужих пользователей
  возвращают `HTTP 403`

## Результаты проверки (локальный прогон)

**До патча** — все три эксплойта успешны:
- SQLi: вход под `admin` без пароля — ✅ подтверждено
- XSS: `<script>` сохранён и отдаётся без экранирования — ✅ подтверждено
- IDOR: прочитаны пароли `admin`, `alice`, `bob` чужим пользователем — ✅ подтверждено

**После применения патча** — все три эксплойта блокированы:
- SQLi: вход под `admin` невозможен — ❌ (ожидаемо)
- XSS: `<script>` отдаётся в экранированном виде — ❌ (ожидаемо)
- IDOR: `/profile/<чужой_id>` → `403 Forbidden` — ❌ (ожидаемо)
